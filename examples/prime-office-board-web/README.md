# PRIME 事務所ボード（Web版）

スタッフ用の共有ウェブアプリ。Claude アカウントを持たないスタッフでも、
メールアドレスとパスワードでログインして使える独立版。

Artifact 版（`../prime-office-board/`）と画面・機能は同じで、データの置き場所と
ログイン方法だけが違う。

本部（プライムグループ本部）が本拠地で、各拠点（ダイア・プライム・桜姫など）の
スタッフは拠点ごとの入り口から入る。本部は拠点をタブで切り替えて、スタッフ側の画面を
そのまま見られる。

- 公開先: <https://prime-office-board.onrender.com>
- データベース / 認証: Supabase（プロジェクト `PRIME Office Board`、東京リージョン）
- ホスティング: Render 静的サイト（`prime-office-board`）。このディレクトリを
  publish path として、ブランチへの push で自動デプロイされる

Render はリポジトリ直下の `package.json` を見て依存インストールを試みるが、
このリポジトリは `packageManager: yarn@4` を指定しており、Render の既定の
Yarn 1.22 では失敗する。このアプリはビルド不要なので、サービスの環境変数に
`SKIP_INSTALL_DEPS=true` を設定してインストール自体を飛ばしている。
リポジトリのルートをこのディレクトリに変更できるなら、そちらのほうが素直。

## 構成

ビルド不要の静的サイト。

| ファイル     | 役割                                            |
|--------------|-------------------------------------------------|
| `index.html` | 全画面ぶんの CSS とマークアップの器             |
| `app.js`     | 状態管理・Supabase アクセス・描画・イベント処理 |

`supabase-js` は CDN から読み込む。ほかに依存ライブラリはない。

サーバー側（スタッフのログインを処理する Edge Function とスキーマの経緯）は
`../prime-office-board-supabase/` にある。Render が publish するのはこのディレクトリ
だけなので、サーバー側のコードが静的サイトとして配信されないように分けている。

## セットアップ（初回のみ）

最初の一人が「アカウント作成」から登録する。`members` が空のうちは誰でも登録
できるので、最初に登録した人が管理者になる。

以降の登録条件は「設定」タブの**スタッフの登録方法**で選ぶ。

| 方法               | 条件                                   |
|--------------------|----------------------------------------|
| 招待コード（既定） | 設定画面に出るコードを知っている人だけ |
| メールアドレス     | 許可リストに載せたアドレスの人だけ     |
| 誰でも             | URL を知っていれば誰でも               |

現在は「誰でも」で運用している。URL の共有先が限られているという判断による。
招待コードに戻すと、コードを知っている人だけが登録できる。コードは口頭や LINE
で伝え、「作り直す」を押すと以前のコードは無効になる。

サインアップ画面は、ログイン前でも `public.signup_mode()`（`anon` に実行権限を
付与した security definer 関数）で現在の方式だけを読み、招待コード欄の出し分けに
使う。招待コードそのものは `board_settings` に残り、メンバー以外は読めない。

Supabase の既定ではメール確認が必須で、無料枠の送信数も厳しいため、
`auth.users` への INSERT 時に走るトリガー `auto_confirm_allowed_trg` が、
登録条件を満たしたアカウントだけを確認済みにする。条件を満たさないアドレスは
未確認のまま残るので、ログインできない。サインアップの応答にセッションが
含まれないことがあるため、画面側は登録直後に同じ資格情報でサインインを試みる。

## 表示

明るい / 暗い / 端末に合わせる の 3 段階を、ヘッダー右端のボタンで切り替える。
選択は `localStorage`（`prime.theme`）に残る。既定は「明るい」で、端末が
ダークモードでも明るい配色で開く。

720px 以下ではタブが画面下部に固定され、表など横に長い表示はカードに切り替わる。

## データベース

| テーブル         | 内容                                                        |
|------------------|-------------------------------------------------------------|
| `members`        | 表示名・色・在席。主キーは `auth.users.id`                  |
| `allowed_emails` | 登録を許可するメールアドレス                                |
| `office`         | 事務所の扉の開閉（1 行のみ）                                |
| `schedule`       | メンバー×日付。区分・予定・やったこと・連絡不可時間帯       |
| `tasks`          | やること。`site_id` が NULL なら本部、値があればその拠点    |
| `payments`       | 支払い予定と、支払い済みの経費メモ                          |
| `vault`          | 媒体アカウント。ID とパスワード                             |
| `shops`          | 店舗の募集条件と、媒体掲載用のプロフィール。`kind` で分ける |
| `sites`          | 拠点。入り口コード・公開の可否・見せるタブ                  |
| `staff`          | 拠点の名簿。暗証番号のハッシュ・鍵の所持                    |
| `punches`        | 出勤・退勤の打刻                                            |
| `key_events`     | 「開けた」「閉めた」の報告                                  |
| `key_duty`       | その日の鍵の開け閉め担当                                    |
| `staff_shifts`   | スタッフ×日付のシフト登録                                   |
| `notes`          | 自分だけのやること・メモ。見せる相手を1件ずつ選べる         |

RLS は全テーブルで有効。本部のテーブルは `members` に行がある利用者だけ、拠点の
テーブルは本部か、その拠点のスタッフだけが読み書きできる（`staff_site()` が
判定する）。`members` への INSERT は、自分の行であり、かつ `allowed_emails` に自分の
メールアドレスがある場合（または members がまだ空の場合）だけ通る。ログインしただけの
利用者には何も見えない。

変更は Realtime で全員の画面に反映される。

## スケジュール

スタッフは全員が個人事業主の業務委託なので、区分は勤怠ではなく「どこで働くか」を表す。

| 区分         | 意味                                             |
|--------------|--------------------------------------------------|
| 事務所       | 事務所に行く。時間も入れる                       |
| 事務所＋在宅 | 半分は在宅、半分は事務所。時間は事務所にいるぶん |
| 在宅         | 自宅で作業                                       |
| 外仕事       | 面接・撮影など外での仕事                         |
| 休み         | 休み                                             |
| 未定         | 未記入                                           |

`from_time` / `to_time` は事務所や現場にいる時間帯、`ng_from` / `ng_to` は連絡が
つかない時間帯で、別物として持つ。`link_url` は面接・撮影の詳細ページなど。
カレンダーのマスには、連絡不可（赤）・予定メモ（真鍮）・リンクあり（青）の
3 色の点が出る。

「事務所＋在宅」（`both`）は、片方だけを選ばせると選ばなかった側の時間が予定から
消えてしまうために足した。カレンダーのマスは事務所の色と在宅の色を斜めに half-and-half
で塗る（凡例にも同じ見本を出す）。時間欄には事務所にいるぶんを入れ、在宅の時間帯は
「今日1日の動き」に書く。

移行時に旧区分の `work` と `half` は `office` に寄せた。

`plan`（これからの予定）と `done`（やったこと）は別のカラムに分けている。予定を
実績で上書きしてしまうと、その日に何を予定して何が実際に終わったのかが残らない
ため。ホームでは予定の下に「やったこと」を緑の縦線付きで並べ、カレンダーのマスには
記録済みを示す緑の点が付く。

## お知らせ・共通予定

`notices` は全員向けの1件1行。全体ミーティングや媒体担当者との打ち合わせのように
日付があるものと、新人が入ったなどの日付のないお知らせを同じ表で扱う（`date` が
null なら後者）。`pinned` を立てると先頭に固定される。

並び順は 固定 → これからの日付 → 日付なし → 過去。ホームには先頭 5 件、
スケジュールタブにはその月ぶんを出す。

## 求人パイプのURL

`board_settings.recruit_url` に入れておくと、スケジュールの「関連リンク」欄に
ワンタップで差し込めるボタンが出る。面接の予定から求人パイプへ直接飛ぶための導線。

## やること（タスク）

本部の「タスク」と拠点の「TODO」は、どちらも「誰かがやる仕事」で中身が同じだったので
`tasks` 一本にまとめた。`site_id` が NULL なら本部、値が入っていればその拠点の仕事。
`staff_todos` は使われないまま削除した。

担当は `assignee`（本部メンバー）と `staff_assignee`（拠点スタッフ）の2列で持つ。
認証の系統が別で参照先のテーブルが違うため、1列にまとめられない。画面では1つの
選択肢にまとめ、値の頭 `m:` / `s:` で振り分ける。

まとめたことで、片方にしかなかったものが両方で使えるようになった。

| もとは                                                           | いまは         |
|------------------------------------------------------------------|----------------|
| 引き受ける・手放す（募集中の仕事を手が空いた人が取る）は本部だけ | 拠点でも使える |
| 終わったときの共有メモは拠点だけ                                 | 本部でも使える |

本部のタスク画面には置き場所の絞り込み（すべて / 本部 / 拠点ごと）が出て、各行に
どこの仕事かが出る。スタッフ側は自分の拠点ぶんだけで、絞り込みも置き場所の欄も出ない。

ホームの「募集中」と、タブの件数バッジは**本部の仕事だけ**を数える。拠点の募集中は
その拠点のスタッフが見るもので、本部のホームに混ぜると本部の状況が読めなくなるため。

## 自分用（自分だけのやること・メモ）

`tasks` は「チーム全員が読めるもの」として作ってあるので、そこに私物を混ぜると、
読み取りポリシーを一箇所間違えただけで全部が見えてしまう。別の表 `notes` に分けて、
規則そのものを「自分のもの」と「見せると決めたもの」だけに限っている。

タスクタブの上の「みんなの / 自分用」で切り替える。タブは増やさない（スマホの
下バーがすでに8つあるため）。ホームにも未完了ぶんを小さく出す。

| `share`   | 見える人                     |
|-----------|------------------------------|
| `private` | 自分だけ（既定）             |
| `some`    | `shared_with` に入れた人だけ |
| `all`     | 本部のメンバー全員           |

- 種類は「やること」（チェックできる・期限つき）か「メモ」のどちらか
- 見せてもらっている側は**読むだけ**。書き換えも削除も持ち主にしかできない
- 拠点スタッフには、共有されていても届かない（`is_member()` を満たさないため）
- チップは「たかし に公開」「たかし から」と向きを添える。名前だけだと、
  見せている相手なのか書いた人なのか読めないため

RLS は次のとおり。読みは `owner = auth.uid()` か、`is_member()` かつ
（`share = 'all'` または `auth.uid() = any(shared_with)`）。作成は自分名義のみ、
更新と削除は持ち主のみ。

## 支払い・経費

`payments` は「これから払うもの」と「もう払ったもの」を 1 つの表で扱う。同じ支出を
予定として登録してから支払済に変えることも、買ったあとに経費メモとして直接記録する
こともできる。

| 列         | 未払いのとき         | 支払済のとき            |
|------------|----------------------|-------------------------|
| `due`      | 期日                 | 使わない（NULL に戻す） |
| `paid_on`  | 空                   | 実際に支払った日        |
| `assignee` | 支払う担当           | 立て替えた人            |
| `category` | 分かっていれば入れる | 経費の区分              |

支払った日を `paid_at`（タイムスタンプ）と別に `paid_on`（日付）で持つのは、
経費が「画面で押した日」ではなく「実際に払った日」の月に入らないと帳簿に使えない
ため。あとからレシートを見て記録するときは、その日付を入れ直せる。

`category` は自由入力で、よく使う区分（広告・媒体掲載料、家賃、備品・消耗品など）を
ボタンと入力候補で出す。決まった選択肢に縛らないのは、区分の呼び方が事務所ごと・
税理士ごとに違うため。空のままの行は「未分類」として集計に出る。

「支払済」で絞り込むと、月ごとの合計と区分別の内訳が表の上に出る。月は
「← 前月 / 今月 / 翌月 →」で移動する。表の列も、期日・担当ではなく支払日・区分に
入れ替わる。

## 店舗

`shops` に 1 店舗 1 行。見出しは店舗ごとにばらばら（12 個の店もあれば 31 個の店も
ある）なので、固定カラムを持たず `sections` に `{label, value}` の配列として
順番どおり保存する。

編集画面は項目ごとの入力欄ではなく、求人票の ■ ブロックをそのまま貼る 1 つの
テキストエリア。`parseShopText()` が次のように解釈する。

- `■` で始まる行が見出し。`■店名：〇〇` のように同じ行に値があっても、
  次の行から書いてあってもよい
- `■施術時の格好` のように値のない見出しも、そのまま残る
- 見出しのない先頭のテキストはラベルなしの節として保持する
- `店名` と `URL` は `name` / `url` カラムに振り分け、`sections` からは除く

「まとめてコピー」は `shopText()` で ■ 形式に組み直す。貼る → 保存 → コピーで
元の体裁に戻るので、応募の返信にそのまま使える。

電話番号だけは `phone` カラムに分けて持ち、■ ブロックには入れない。ブロックに
混ぜると、コピーして貼り直すたびに見出しとして増えてしまうため。カード上では
`tel:` リンクになるので、スマホからそのまま掛けられる。表示は入力どおりで、
発信するときだけ数字に直す（全角やハイフンが混じっていても掛かる）。
掲載用プロフィールの側には欄そのものを出さない。

### 掲載用プロフィール

同じタブの中で **店舗 / 掲載用プロフィール** を切り替える。媒体に載せるキャストの
プロフィールも、店舗の求人票と入れ物としては同じ——見出しと値を順番どおり持って、
そのままコピーして貼る——ので、テーブルを分けずに `shops.kind`（`shop` / `cast`）で
仕分けている。新規は開いている側の種別で作られ、編集は元の種別を保つ。

ここに置くのは**掲載用の情報だけ**。在籍しているキャストの本名・生年月日・身分証は
求人パイプ（`recruitment-pipeline`）が持つ。実在しない掲載用プロフィールを求人パイプに
入れると応募者の集計が狂い、本名や生年月日をこのボードに置くと店舗スタッフから
見えてしまうため、置き場所を分けている。

「【ひな形】プロフィール作成シート」は、新しく入った子に送って埋めてもらうための
空欄のシート。

## 拠点とスタッフ

本部のメンバーは `members`、各拠点のスタッフは `staff` で、別の入り口から入る。

|            | 本部                         | スタッフ                                   |
|------------|------------------------------|--------------------------------------------|
| 入り口     | 素の URL                     | `?s=<入り口コード>`                        |
| ログイン   | メールアドレスとパスワード   | 自分で登録した名前と暗証番号4桁            |
| 見えるもの | 全タブ＋全拠点のスタッフ画面 | 自分の拠点の勤怠・鍵・やること・シフトだけ |

本部の画面は支払いやID/パスまで含むので、拠点のスタッフがそこに入れないことが要件
そのもの。スタッフのログインで作られる認証ユーザーは `members` に行を作れないよう、
`may_join()` が「`staff` に紐づく認証ユーザーではないこと」を条件に加えている。

### スタッフの登録

スタッフは入り口の URL を開いて、**自分で名前と暗証番号（4桁）を登録する**。本部が
一人ずつ発行して伝える手間をなくすため。登録するとそのままログインした状態になる。

- 名簿が空のうちは、いきなり登録の画面から始まる。名前が入っていればログイン画面が先で、
  「はじめての方は」から登録に切り替える
- 同じ拠点に同じ名前は登録できない。1拠点40人まで（URL を知っていれば誰でも登録できるので、
  いたずらで際限なく増えないように）
- 本部が拠点ごとに**受付を止められる**。全員そろったら止めておく
- 暗証番号を変えるのは、スタッフ画面の右上にある自分の名前から

### 暗証番号

**本部は4桁をそのまま確認できる**。忘れた人に伝えられるようにするため、`staff.pin` は
戻せる形で持っている。4桁は候補が1万通りしかなく、bcrypt にしても総当たりは一瞬で
終わるので、ハッシュ化しても「テーブルを読めた相手」への守りにはならない。見せる要件と
両立しない見かけだけの防御はやめて、**誰が読めるか**を絞る方に寄せた。

- `pin` 列は `anon` / `authenticated` のどちらからも読めない。Supabase は `public` の
  全テーブルに表単位の権限を配るので、表単位の権限をいったん剥がしてから見せてよい列だけを
  grant し直さないと、列単位の `revoke` は効かない
- 4桁を読めるのは `staff_pin_of()` 経由の**本部だけ**。店長でも他人の番号は見られない
- 照合は Edge Function `staff-login`（`service_role`）の中だけで行う。呼ぶのは
  `staff_check_pin()` で、この関数は `anon` / `authenticated` から実行できない
- 5回続けて間違えると10分ロックする（`staff_login_attempts`）。暗証番号を変えると解除される
- 照合に通ったときだけ、その人ぶんの認証ユーザーにマジックリンクを1回発行し、
  ブラウザ側が `verifyOtp` で通常のセッションに引き換える。これで以降のデータアクセスは
  すべて普通の RLS で守れる

本部から見えるということは、**他のサービスで使っている番号を入れてはいけない**という
ことでもある。登録と変更の画面にはその旨を出している。

### 公開権限

拠点ごとに本部が決める。

- **入り口の公開** — 止めると、登録済みのスタッフもログインできなくなる。`staff_site()` が
  `sites.open` を見ているので、セッションが残っていてもデータが読めない
- **見せるタブ** — 勤怠・鍵・TODO・シフトを個別に出し入れできる
- **新規登録の受付** — スタッフが自分で登録できるかどうか
- **名簿と暗証番号** — スタッフの追加・停止・削除は本部（と、その拠点の店長）。
  4桁の確認は本部だけ

入り口コードがそのまま URL になるので、初期値には推測されにくい4文字を付けてある
（`dia-2331` など）。合言葉を置かない代わりに、このコードが入り口の鍵になっている。

### 勤怠

プライムレジェンドのスタッフアプリと同じ形にした。大きな打刻ボタン、勤務中の一覧、
日付ごとの履歴、店長と本部だけができる手動の追加と修正。

打刻は時刻そのもの（`punched_at`）で持ち、出勤→退勤の順に組にする。夜勤が日付を
またいでも、その勤務は**出勤した日**に残す。前日21時から翌朝5時までの勤務が翌日の欄に
現れてしまうと、その日の人数が実態と合わなくなるため。

### シフト

見えるよう横スクロールを合わせる。

## ID /パス

`vault` に 1 アカウント 1 行。媒体名・店舗・キャスト・URL・ID・パスワード・メモを
そのまま保存する。画面上は ID とパスワードだけ伏せ字で、「表示」を押すと見える。
ログインできるスタッフは全員が読める。

件数が増える前提なので、一覧は「まとめ方」で **媒体別 / 店舗別 / キャスト別 /
まとめない** を切り替えられる。選択は `localStorage`（`prime.vaultGroup`）に残る。
値が空の行は「店舗なし」などのグループに集めて最後に置く。まとめ方に使っている列は
表から省く（店舗別で見ているときに全行へ同じ店舗名を出しても読みにくいため）。

まとめたときは、グループごとに色が付く。見出しは色の帯になり、表の左端にも同じ色の
線が入るので、スクロール中でもどこの塊を見ているかが分かる。色は名前から決めるので、
同じ媒体はいつも同じ色になる（並び順から決めると、1件足しただけで全部の色が入れ替わって
覚え直しになる）。ただし**先に使われている色に当たったときは次の空きにずらす**——
違うものが同じ色で並ぶと、色を付けた意味がなくなるため。色は8色で、それを超えると
一巡する。媒体の色は表の中の媒体名の前にも点として出るので、まとめ方を変えても、
検索で絞っても、同じ媒体は同じ色のまま追える。

検索は媒体・店舗・キャスト・URL・ID・メモを対象にする。**パスワードは検索対象に
含めない** ——パスワード文字列で行を引き当てられないようにするため。検索とまとめ方の
変更は一覧部分だけを描き直すので、入力中にフォーカスが外れない。

店舗とキャストの入力欄には、登録済みの店舗名と既存の値が候補として出る。

「コピー」は `navigator.clipboard` を使い、失敗したときは `execCommand` に落とす。
LINE などのアプリ内ブラウザでは前者が無いことがあるため。空の値をコピーしたときは
成功と言わずにその旨を出す——貼れない理由が分からなくなるため。

以前は共有の合言葉で AES-GCM 暗号化していたが、運用の手間に見合わないという
判断で外した。戻す場合は `vault` の `login_id` / `password` を暗号文カラムに
置き換え、鍵導出をブラウザ側に戻す。

銀行やクレジットカードの認証情報は置かない前提。

## ローカルで動かす

`index.html` をブラウザで開くだけでよい。Supabase には本番と同じプロジェクトに
つながるので、試すときはテスト用のアカウントを使う。
