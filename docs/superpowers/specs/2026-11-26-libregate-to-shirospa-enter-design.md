# リーブルゲートから しろspa へ、ログインなしで入る

- 日付：2026-11-26
- 大きさ：小さめの変更（関数1つ＋ボタン1つ＋設定）

## ねらいと理由

リーブルゲートのボードのホームに「関わっている会社のボード」という欄があり、
そこの「開く」で しろspa のボードが新しいタブで開く。ただし開いた先は別のボード
（別の Supabase）なので、**しろspa のログインを別に求められる**。
リーブルゲートの人は しろspa の仕事も一緒にするので、2回目のログインは要らない。

リーブルゲートに入れていること自体を身分証として使い、
**押したらログイン済みで しろspa に入る**ようにする。

## やること

- リーブルゲートで「開く」を押した人が、しろspa にログイン済みで入れる。
- 入った人は **しろspa の本部メンバー**になる（ユーザーの指示：「一緒に書き込む」）。
  お知らせ・支払い・書類など、しろspa の本部メンバーができることは全部できる。
- 名前と色はリーブルゲートのものを持っていく。
- 2回目以降は、同じアカウントを使い回す（毎回増やさない）。

## やらないこと

- 逆向き（しろspa → リーブルゲート）。今の片方向のまま。
- 「見るだけ」の権限。全部の表の見える範囲を作り直すことになるため。
- 藤澤家のボード。欲しくなったら、同じ形で1行足すだけで足りるようにしておく。
- リーブルゲートに入れる人を選り分けること。**リーブルゲートの本部メンバーは全員入れる。**

## 失敗の形（これが起きたら失敗）

- 他の2つのボード（しろspa 単体で入る人・藤澤家）の動きが変わる。
- しろspa に前からいるメンバーのログインが壊れる。
- service_role キーや秘密がブラウザに出る。
- しろspa のメンバーが、押すたびに増える。

## 制約

- **1社＝1 Supabase プロジェクトは崩さない。** 表をまとめない。
- `app.js` と `index.html` は3つのボード共通。新しい動きは
  `config.js` の設定が無ければ一切出ないこと。
- 秘密は Supabase の Secrets にだけ置く。会話にもリポジトリにも書かない。
- 四角い角のまま（丸角にしない）。白地・はっきりした色。

## 考えた3つのやり方

| | 中身 | 引き換え |
|---|---|---|
| **A（採用）** | しろspa に「入場券を出す窓口」を1つ足す。リーブルゲートの証明を見せると、1回だけ使える入場券が返る | リーブルゲートに入れる人は全員 しろspa にも入れる。離れた人の しろspa 側の行は手で消す |
| B | 2つのボードを1つの Supabase にまとめる | ログインは本当に1つになるが、1社＝1プロジェクトを崩し、2社のデータが同じ表に並ぶ |
| C | しろspa の中身をリーブルゲートの画面に出す（開かずに済ます） | ログインの話は消えるが、しろspa の機能を全部もう一度作ることになる |

**A を採った。** B は決まりを崩す。C は仕事が大きすぎる。
A は、このボードに**すでに2回使われている作り方の3つめ**にあたる
（スタッフの暗証番号ログイン `functions/staff-login`、LINE ログイン
`functions/line-login`。どちらも service_role で本人を確かめ、
1回だけ使えるマジックリンクを発行して、ブラウザが `verifyOtp` で
普通のログイン状態に引き換える）。新しい発明が無い。

## 決めたこと（作り）

### 1. しろspa に窓口を1つ足す：`functions/partner-enter`

service_role で動く。受け取るのは、リーブルゲートのログイン証明（access_token）1つ。

1. リーブルゲートの `/auth/v1/user` にその証明を見せて、**本物か**を確かめる。
   → 本人の id が返る。偽物・他のプロジェクトのものはここで落ちる。
2. リーブルゲートの `/rest/v1/members?id=eq.<id>&select=name,color` を、
   同じ証明で読む。**行が返ればその人は本部メンバー**（RLS がそう決めている）。
   名前と色も同時に手に入る。行が無ければ断る。
3. しろspa 側の認証ユーザーを見つける／無ければ1人作る。
   宛先は `lg-<リーブルゲートのid>@partner.prime-office-board.invalid`
   （既存の `staff-...@staff.prime-office-board.invalid` と同じ考え方。メールは送らない）。
4. しろspa の `members` に、その人の行を入れる／名前と色を更新する。
5. 1回だけ使える入場券（マジックリンクの token hash）を返す。

env（公開値のみ。秘密ではない）：
`PARTNER_URL`（リーブルゲートの Supabase URL）、`PARTNER_ANON`（その publishable キー）。
この2つで「どのボードからの入場を受け付けるか」が決まる。
藤澤家を足すときは、ここを複数受け付ける形にする。

### 2. リーブルゲート側：`config.libregate.js` の clients に行を足す

```
clients: [
  { name: "しろspa（ナディア滋賀店）",
    url: "https://shirospa-board.onrender.com",
    enter: "https://qnmkzhjkgaaeqqnplubd.supabase.co/functions/v1/partner-enter",
    enterKey: "<しろspa の publishable キー>" }
]
```

`enter` が無い行は、**今までどおり URL を開くだけ**。だから他のボードは何も変わらない。

### 3. ボタンの動き（`app.js`）

`enter` がある行のボタンは「開く」から **「開く（ログイン済み）」** になる。

1. 押した瞬間に、空のタブを開く（あとで開くと、ブラウザに止められる）。
   そのタブには「入っています…」と出す。
2. 窓口を呼んで入場券をもらう。
3. 空のタブを `https://shirospa-board.onrender.com/?enter=<入場券>` に飛ばす。
4. 失敗したら、そのタブを ふつうの URL に飛ばす（ログイン画面が出る）。
   元のタブには理由を出す。

### 4. しろspa 側の受け取り（`app.js`）

起動時に `?enter=` があれば `verifyOtp({ token_hash, type: "email" })` で
ログイン状態に換え、**URL からすぐ消す**（`history.replaceState`）。
`?enter=` が無いボードには何も関係しない。

### 5. 名前の見え方

しろspa のメンバー一覧には、リーブルゲートで使っている名前がそのまま並ぶ。
（私の判断。「（リーブルゲート）」のような印は付けない。欲しければ後から足せる。）

## 作る人に任せること

- 窓口の断り方の文言（「このボードからは入れません」など）。
- 入場券をもらうまでの待ち時間の出し方。
- テスト：窓口の各分岐（偽の証明・メンバーでない人・2回目）と、
  ボタンが `enter` の無い行では今までどおりであること。

## 分かっている引き換え

- リーブルゲートの本部メンバーは、全員 しろspa に入れる。
- 人がリーブルゲートを離れたら、**しろspa 側のメンバー行は手で消す**。
  入場はできなくなるが、名前は残る。
- リーブルゲートの証明が、いちど しろspa の窓口を通る（確かめるためだけに使い、
  保存しない）。どちらのボードも同じ人が持っているので、これでよいと判断した。
